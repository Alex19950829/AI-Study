Lilian Weng 经典 Agent 拓扑架构

源自前 OpenAI 研究副总裁 Lilian Weng（翁荔）2023 年开创性论文《LLM Powered Autonomous Agents》。

🦀

经典理论基石：LLM 居中当大脑，四大器官向外延伸

2023 年 6 月提出的经典拓扑结构：Agent (LLM) 居中作为大脑，向四周延伸出 Planning 规划、Memory 记忆、Tools 工具与 Action 行动 4 大核心模块，奠定了现代所有 Agent 框架的底层拓扑。

1. Planning (规划模块)

• Subgoal Decomposition：大目标拆解为微任务序列
• Reflection & Self-criticism：反思与自我纠错
• Chain of Thoughts：思维链逻辑推演

2. Memory (记忆模块)

• Short-term Memory：Context Window 维持会话上下文
• Long-term Memory：向量数据库 (RAG) 跨会话召回
• 历史沉淀：工具执行日志与交互记录

3. Tools (工具库延伸)

• 外部能力扩展：Calendar() / Calculator() / Search()
• Code Interpreter：代码解释器与沙箱环境
• 状态感知：抓取真实环境 Observe 返回值

4. Action (行动与交付)

• 环境副作用：修改真实代码、发送邮件、提交订单
• 闭环交付：完成复杂长链路任务后输出结构化结果
• 动态触发：Action 输出触发新一轮 Observe 观察

💡 一句话总结：大模型是大脑（Brain），而 Planning（规划）+ Memory（记忆）+ Tools（工具）+ Action（行动） 共同构成了自主 Agent 的完备结构。

Planning - Action - Observe 控制循环

普通 LLM 是单向问答（Input ➔ Output）；Agent 是闭环自愈系统（Input ➔ [Plan ➔ Act ➔ Observe] × N ➔ Output）。

多工具编排：并发 vs 串行与智能分批

模型一次返回多个 tool_calls 请求，框架层如何高效、安全地调度与并发执行。

⚡

原生 Parallel Tool Calling：LLM 预测多个请求，框架控制并发策略

当用户发出复合需求时，大模型在单次响应中返回 多个 tool_calls 数组。模型始终只输出结构化 JSON，真正的并发调度、写冲突防护与异步执行由工程框架代码掌控。

1. 绝对串行 (Serial)

• 调度机制：一个接一个顺序执行
• 安全评估：防数据竞争，最安全但整体响应较慢
• 适用场景：强依赖任务（查用户ID ➔ 查订单）

2. 完全并发 (Parallel)

• 调度机制：所有工具异步同时发起
• 响应速度：体验最好，耗时由最慢工具决定
• 适用场景：无写冲突的纯只读查询

3. 智能分批 (Smart Batching)

• 调度机制：按安全标记自动分组调度
• 架构选型：兼顾体验与安全的工程最佳实践
• 适用场景：写操作单独跑，查询操作合并跑

💡 工程最佳实践：工具定义中标注安全等级。只读查询采用异步并发提速，有副作用或数据竞争的写操作分批串行，兼顾极致体验与系统安全。

黄金判定法则：你的业务适合做 AI Agent 吗？

避免盲目套用概念！通过 3 大关键维度 与 控制权归属矩阵 精准评估落地可行性。

AI Agent 可行性三大硬性指标

1. 🔧 工具可感知性 (Tool Availability)
是否有明确的 API、Shell 终端、数据库或 DOM 接口可供 Agent 调取并作用于真实环境。
2. 🔄 过程容错与自愈性 (Fault Tolerance)
中间步骤是否允许“试错”。Agent 的本质是探索反馈，环境报错能够作为新的 Observe 信号。
3. 🎯 结果判定客观性 (Objective Criteria)
人类或代码是否拥有确切的最终验收标准（如：测试全绿、SQL正常返回、导出的表格格式规范）。

控制权归属：AI 工作流 vs AI Agent

对比维度 AI 工作流 (Workflow) AI Agent (智能体)
控制核心 程序员硬编码 If/Else LLM 大脑动态决策
执行路线 确定性单向/分支流水线 [Plan-Act-Obs] × N 闭环
异常处理 抛出 Error / 预设中断 抓取报错并自主修正

⚖️ 落地决策建议：流程完全确定且不允许试错 ➔ 选择 AI 工作流；目标确定但路径未知、需要环境反馈与容错自愈 ➔ 选择 AI Agent。

上下文窗口拆解与各框架 Message List 存储位置

从算力物理硬伤到主流 Agent 框架（OpenClaw / LangChain / AutoGen / Claude Code）的内存与持久态存储机制。

⚡ 1. 为什么必须设窗口？三大物理算力硬伤
💥 ① KV Cache 显存暴胀 (OOM 崩溃)
每个 Token 缓存约占 1.2 KB。无节制保留超长 Session 会瞬间吃掉上百 GB 显存引发 OOM 崩溃。
⬛ ② 自注意力 O(N2) 算力黑洞与天价账单
计算复杂度呈平方级增长（10 万 Token 计算量暴增一万倍！），首字延迟飙升且计费累加攀升。
🧠 ③ 注意力稀释 (中间失忆 Lost in the Middle)
上下文过长会导致注意力分布被极度平摊，模型极易遗忘中段核心约束与 System Prompt。
🗄️ 2. 主流 Agent 框架 Message List 存储位置

OpenClaw /compact 自动压缩与写回全流程

解剖 OpenClaw 上下文警示与 /compact 斜杠指令：从消息分割、后台摘要到持久化覆盖写回。

⚠️ 1. OpenClaw 水位警示与 /compact 触发
CLI 水位警示： 当上下文占用达到 ~78% 时，CLI 自动输出：
Context window is 78% full. Run /compact to condense history.
🔄 2. 执行 /compact 后底层 6 步动作
Step 1: 消息冻结与三段分割 ➔ 拆分为 System + 待压缩旧历史 + 最近3轮
Step 2: 构造专用 Summary Prompt ➔ 要求保留需求、决策、未竟目标，抛弃废话
Step 3: 唤醒后台 LLM 摘要 ➔ 独立 API 请求，将上万 Token 浓缩为 300 字
Step 4: 消息数组极简重构 ➔ 组装 [system+summary, *recent_3_turns]
💾 3. 本地写回与 CLI 反馈
Step 5: 覆盖写回持久化存储
• SQLite 模式：更新 openclaw.db 的 session_id 消息记录。
• JSON 模式：覆盖更新 ~/.openclaw/storage/sessions/<id>.json。
Step 6: Token 重置与 CLI 成功反馈
• Tiktoken 重新计算 Token (从 182,400 降至 14,200 Token)。
• 终端打印：✓ Context compacted! Reduced from 182.4K to 14.2K (Saved 92%).
💡 架构实战意义：通过斜杠指令或自动检测，将复杂的摘要、切片与数据库覆盖写回封装为无感命令，既保障了记忆连续，又免除了显存 OOM 崩溃。

Claude Code 自动压缩与代码状态锁定

解剖 Anthropic 官方 CLI Agent：160K 警戒线、Git 与文件修改锁定、.jsonl 追加存储。

📁 1. Claude Code 本地存储位置
• 核心会话日志：~/.claude/transcripts/<session_id>.jsonl (JSON Lines)
• 会话元数据：~/.claude/projects/<slug>/state.json (关联 Git 与开销)
• 全局配置/缓存：~/.claude/config.json 与 cache/ (文件树全景图)
⚙️ 2. 执行 /compact 的 5 个工程动作
1. 代码与 Git 状态锁定 ➔ 强行保护已被修改的文件路径、Diff 与项目树
2. 超长工具报文二次清洗 ➔ 截断 Bash/Grep/Log（如 5000 行 test log 切为关键报错）
3. 唤醒工程背景摘要 ➔ 总结已改代码、测试通过情况与待办 Task
🔄 3. 消息重构、追加写回与 UI 反馈
4. 消息数组极简重构
组装全新的 [System + 代码工程摘要 + 最近 2~4 轮原始对话]。
5. 追加写入 .jsonl 与 UI 清零
• 覆盖更新 state.json 元数据，并将压缩结果追加写入 .jsonl 日志。
• 终端转圈提示：✓ Compacting context (165.4K ➔ 12.3K tokens)...
💡 核心特色：不同于普通对话聊天，Claude Code 优先保证代码改动与 Git 分支上下文不丢，专门针对代码重构与大型工程修补设计。

OpenClaw vs Claude Code 上下文治理全景对比

通用 Agent 框架与代码重构 Agent 框架在存储介质、压缩侧重、代码保护与报文清洗四大维度的深度对比。

对比维度 🤖 OpenClaw (通用 Agent 框架) 💻 Claude Code (代码重构 CLI Agent)
1. 存储介质与格式 本地 SQLite 数据库 (openclaw.db) 或按 Session 划分的独立 .json 文件。 项目级 JSON Lines (~/.claude/transcripts/*.jsonl) 文本日志 + state.json。
2. 压缩关注焦点 偏向通用对话与业务状态：保留用户原始诉求、核心身份偏好、已达成决策与未竟目标。 偏向工程代码与测试状态：保留已修改文件路径、构建报错信息、已通过测试与待办 Task。
3. 代码与状态保护 依赖通用 System Prompt 归纳背景摘要。 强行锁定机制：绝不删除已修改文件清单、Git Diff 变更与项目文件树结构。
4. 工具报文清洗 正则匹配 role="tool" 消息，提取 summary 字段清洗 raw JSON/HTML。 针对 Bash / Grep / Edit 终端输出，按行数与报错关键字做硬裁切（如 5000 行切为前 200 行）。

💡 选型结论：通用业务 Agent 优先参考 OpenClaw 的 SQLite + 全局结构化摘要模式；代码重构与 IDE 插件 Agent 必须参考 Claude Code 的文件修改锁定与超大日志截断机制。

通用 Agent 消息列表 4 大压缩算法与四层防线

从基础滑动窗口到向量 RAG 检索，结合水位阶梯式防线实现极端长对话不中断崩溃。

⚡

1. 滑动窗口法 (Trimming)

messages = [system] + history[-K:]
0 成本毫秒级，但易误删早期关键约束。
📝

2. 带摘要滑动窗口 (Summary Buffer)

messages = [system, summary] + history[-K:]
OpenClaw / LangChain 推荐，记忆保鲜且降本 90%。
🎯

3. 向量检索注回法 (Vector RAG)

旧对话写入 Chroma/FAISS 向量库，按 Top-K 检索注入，适合长对话陪伴。
🌳

4. 树形递进折叠 (Tree Summary)

每 10 轮合成小节点、每 5 个合成大节点，适合超长学术/代码重构。

🛡️ 四层渐进式防线：60% 裁剪 Snip (删 Raw 工具数据) ➔ 75% 微压缩 Micro (剔除废话) ➔ 85% 折叠 Collapse (小模型背景摘要) ➔ 95% 紧急 AutoCompact (仅留 System + 摘要 + 近3轮)，实现长 Agent 永不崩溃。

MCP (Model Context Protocol) 架构解耦与跨平台工具标准

从“混乱工具调用 (N×M)”到“开放标准协议 (N+M)”：Client 与 Server 的彻底解耦与生态互通。

🔌 1. Client 与 Server 的彻底解耦
• Client 端 (Agent / Host)：如 Cursor、Claude Desktop、OpenClaw。
仅遵循 JSON-RPC 2.0 发送标准指令：
1. tools/list ➔ 查询有哪些可用工具与入参 Schema
2. tools/call ➔ 传入参数并获取工具返回 JSON
• Server 端 (工具/数据提供方)：如 GitHub、Postgres MCP Server。
内部具体怎么连数据库、调 API、跑 Python 或做缓存重试，Client 端完全不可知也不必关心。
🌟 2. MCP 解决的核心痛点（AI 界的 LSP 革命）
① 语言无关 (Language Agnostic)：Server 可用 Python/Go/Node/Rust 编写，走 Stdio 管道或 SSE (HTTP) 通信。
② 进程级安全隔离 (Process Isolation)：Server 运行在独立沙箱/进程中，崩溃不影响 Agent 主系统。
③ 一次开发，全生态复用 (N+M 模式)：1 个标准 MCP Server 可同时挂载到 Cursor、Claude、自研 Agent 等所有宿主。
💡 架构定位：MCP 不只是框架内的规范，而是由 Anthropic 官方开源并推动的全行业跨平台开放标准协议，彻底打破了模型与外部物理工具/数据的孤岛壁垒。
🔄 端到端闭环协同机制：
• 初始化拉取：Client 宿主在连接时自动通过 tools/list 获取工具清单与 Schema，随用户提问一并喂给大模型；
• 大模型意图决策：大模型推理后下达调用意图与参数（tool_calls），由 Client 代理向 MCP Server 发起物理 tools/call 调用；
• 结果回传与推理：Client 将获取到的工具 JSON 结果包装为 role: "tool" 再次喂回大模型，由模型完成最终回答或进入下一轮链式推理。
